# Gate 3 — the distributed payload

**Check the ZIP, never the working tree.** The dev tree is full of files that never ship,
and it hides files that should ship but do not. Build the real archive, extract it under
its real slug directory name, and check *that*.

```sh
# the ZIP must not sit inside the plugin directory — file_type/compressed_files fires
mkdir -p /tmp/pkg && mv my-plugin-*.zip /tmp/pkg/ && cd /tmp/pkg && unzip -q my-plugin-*.zip
```

`scripts/pcp-gate.sh` does all of this, and warns if an archive ships inside the payload.

## What the reviewer expects to find

Only what production needs: `php`, `js`, `css`, `txt`, `md`, some media (`png`, `svg`,
`jpg`), and data files (`json`, `xml`).

Two deliberate exceptions worth keeping:

- **Readable source** you ship to satisfy the human-readable-code guideline.
- **Config files needed to rebuild assets** — `composer.json`, `package.json`. Removing
  `composer.json` while shipping `vendor/` produces `missing_composer_json_file`.

The ones that catch people out:

| Code | What it means |
|---|---|
| `ai_instruction_directory` | `.claude/`, `CLAUDE.md`, `.cursor/`, `AGENTS.md` and friends. **New, and easy to ship by accident** — these live in most working repos now. |
| `hidden_files` | Any dotfile outside `vendor/`, `node_modules/`, `vendor_prefixed/` — `.gitignore`, `.editorconfig`, `.distignore` itself. |
| `github_directory` | `.github/` |
| `unexpected_markdown_file` | Markdown beyond the expected set |
| `compressed_files` | A `.zip`/`.tar.gz` inside the payload — including the build output, if you left it there |
| `phar_files` | Any `.phar` |
| `application_detected` | Binaries and executables |
| `badly_named_files` | Names that will not survive every filesystem |
| `case_sensitive_files` / `case_sensitive_folders` | Two paths differing only in case — breaks on macOS/Windows |
| `library_core_files` | A bundled copy of WordPress core, or of another plugin |
| `missing_composer_json_file` | `vendor/` ships without its `composer.json` |
| `five_star_reviews_detected` | (`plugin_content`) Soliciting five-star reviews |

Also relevant here:

- **`direct_file_access`** — every PHP file needs `defined( 'ABSPATH' ) || exit;` or
  equivalent at the top.
- **`minified_files`** — a minified asset must ship its source, **or** the readme must
  link publicly accessible build tooling. Guideline 4 requires *source code and any build
  tools* to be publicly accessible: a ZIP that excludes `tools/` therefore **requires** the
  readme link.
- **`code_obfuscation`** — see `justifying-false-positives.md`.
- **Bundled translations** — ship only the `.pot`. `.po`, `.mo`, `.l10n.php` and `.json`
  are delivered by translate.wordpress.org after publishing; shipping them is discouraged.
- **Screenshots** belong in SVN `assets/`, never in the ZIP.
- **Bundled libraries** must be on their latest **stable** release, and you should use
  WordPress's bundled jQuery / PHPMailer / SimplePie rather than shipping your own
  (guideline 13).

Keep `composer.json` if `vendor/` ships. Keep `package.json` if the readme points at it as
the build tooling.

> **If your build script has its own hard-coded copy list** — as
> `create-wordpress-org-compliant.sh` does — then `.distignore` alone is not enough.
> **Both** must be updated whenever a shipped file is added or removed. Missing this ships
> a broken package, and the ZIP is what gets reviewed.

Verify the package manifest after building:

```sh
find my-plugin -type f | sed 's|^my-plugin/||' | sort
find my-plugin -name '*.php' -exec php -l {} \; | grep -v "No syntax errors"
```

## Where a plugin may write

No PHPCS sniff covers this fully; the reviewer does. In order of preference:

1. **The database**, via the Settings API — especially for privileged data.
2. **The media library**, via the media uploader, for user media.
3. **`uploads/<slug>/`**, resolved at runtime with `wp_upload_dir()` — never a hard-coded
   path. Create a folder named with the plugin slug. If the data is not public, protect it
   from direct access.

Not allowed: the plugin's own folder, another plugin or theme, core directories, or any
arbitrary user-supplied path. Writing directly into `wp-content/` is acceptable **only**
when the plugin's nature genuinely requires it (caching drop-ins, backup storage) — expect
to justify it.

```php
private function resolve_output_path( string $output ): string {
    $uploads = wp_upload_dir();
    if ( ! empty( $uploads['error'] ) ) {
        return new WP_Error( 'mypfx_uploads', $uploads['error'] );
    }
    $dir = trailingslashit( $uploads['basedir'] ) . 'my-slug';
    if ( ! wp_mkdir_p( $dir ) ) {
        return new WP_Error( 'mypfx_mkdir', "Could not create directory: {$dir}" );
    }
    // basename() discards directory components; sanitize_file_name() discards traversal.
    $name = sanitize_file_name( basename( $output ) );
    return trailingslashit( $dir ) . ( '' === $name ? 'output.json' : $name );
}

require_once ABSPATH . 'wp-admin/includes/file.php';
WP_Filesystem();
global $wp_filesystem;
$wp_filesystem->put_contents( $file, $data, FS_CHMOD_FILE );  // also clears AlternativeFunctions
```

For "write anywhere" ergonomics in a CLI command, print to STDOUT and let the user
redirect (`wp my-cmd > /any/path`) rather than accepting a path to write to.

Detect:

```sh
grep -rnE --include='*.php' --exclude-dir={vendor,node_modules,.git,tests,dist,build} \
  "file_put_contents|fopen|fwrite|fputs|mkdir|unlink|rename\(|copy\(" .
```

## Locating your own files

Never rely on WordPress *internal* location constants (`WP_PLUGIN_DIR`, `WP_CONTENT_DIR`,
`ABSPATH`, `WPMU_PLUGIN_DIR`) to find your own plugin — they vary per install (custom
`wp-content`, symlinks, multisite). Anchor to `__FILE__` in the main file:

```php
define( 'MYPFX_FILE', __FILE__ );
define( 'MYPFX_DIR',  plugin_dir_path( __FILE__ ) );
define( 'MYPFX_URL',  plugin_dir_url( __FILE__ ) );

require_once MYPFX_DIR . 'includes/thing.php';
wp_enqueue_script( 'mypfx-app', plugins_url( 'js/app.js', MYPFX_FILE ), array(), MYPFX_VERSION, true );
```

## Already published? Check SVN too

Plugin Check 2.1.0 ships an SVN Checker (*Tools → Plugin Check SVN*) that scans a
plugin's wordpress.org SVN repository for unexpected files, folders and zip archives in
`trunk`, `tags` and `assets`.

```sh
svn ls https://plugins.svn.wordpress.org/<slug>/trunk/
svn ls https://plugins.svn.wordpress.org/<slug>/tags/
curl -s https://plugins.svn.wordpress.org/<slug>/trunk/readme.txt | head -8
```

`Stable tag` must name a tag that actually exists in that list. If it does not, the
directory silently serves **trunk** instead — which is how a version nobody tagged ends up
being what users download.

**SVN history is permanent.** A secret committed there is not undone by deleting the file;
only regenerating the credential helps. `.gitignore` does not apply to SVN.
